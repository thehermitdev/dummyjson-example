## 1. เป้าหมายของ Carts Feature

Carts ในโปรเจ็กต์นี้มี scope ชัดเจน:

```text
GET /carts
GET /carts/:id
GET /carts/user/:userId
```

เรา **ไม่สร้าง Add/Update/Delete Cart** เพราะ requirement ของ Admin Example ต้องการใช้ Carts เป็น read-oriented commerce view เท่านั้น

นี่เป็นบทเรียนสำคัญ:

> การมี `mutations.ts` ใน Users/Posts ไม่ได้แปลว่าทุก feature ต้องมีไฟล์นี้

โครงสร้างควรสะท้อน use case จริง

# Phase 1 — เข้าใจ Cart Domain

## Step 1 — อ่าน Cart shape ก่อนสร้าง UI

Cart ไม่ใช่แค่ id + userId แต่มี nested products:

```text
Cart
├── id
├── userId
├── total
├── discountedTotal
├── totalProducts
├── totalQuantity
└── products[]
    ├── id
    ├── title
    ├── price
    ├── quantity
    ├── total
    ├── discountPercentage
    ├── discountedTotal
    └── thumbnail
```

สิ่งนี้ส่งผลกับ:

- Zod schema ต้อง nested
- Detail page ต้องแสดง products table/list
- list page ไม่ควรโหลด/render product detail ทั้งหมดเกินความจำเป็น

# Phase 3 — API Client

## Step 3 — สร้าง `client.ts`

Reference:

- [Carts API Client](https://github.com/thehermitdev/dummyjson-example/blob/main/src/features/carts/api/client.ts)

List input มีเพียง:

```text
page
pageSize
userId?
```

Client responsibilities:

```text
page/pageSize
-> convert เป็น limit/skip

ไม่มี userId
-> GET /carts

มี userId
-> GET /carts/user/:userId
```

### ทำไม endpoint selection อยู่ Client

Route ต้องรู้ว่า user เลือก owner คนไหน แต่ไม่ควรรู้ว่า DummyJSON ใช้ URL `/carts/user/:id` เพราะนั่นเป็น transport detail

---

## Step 4 — Pagination Formula

เหมือน Users/Posts:


ให้เก็บ formula ใน client ไม่กระจายตาม component

### Cache Policy

| Query | staleTime |
|---|---:|
| Carts List | 60s |
| Cart Detail | 5m |

### เหตุผลที่ Detail cache นานกว่า List

Cart detail ที่เคยเปิดแล้วมี product breakdown ค่อนข้างแพงกว่า list row ในเชิงข้อมูลและไม่จำเป็นต้อง refetch ทุก navigation ขณะที่ list filter/pagination เปลี่ยนบ่อยกว่า

## Step 10 — Owner Filter เป็น Immediate Filter

Owner เป็น `<select>` จึงไม่ต้อง debounce

Flow:

```text
select User #5
-> update URL userId=5
-> reset page=1
-> query key เปลี่ยน
-> /carts/user/5
```

URL ตัวอย่าง:

```text
/carts?page=1&pageSize=10&userId=5
```

# Phase 13 — ทำไมไม่มี Cart Mutations

นี่เป็น section ที่ต้องเข้าใจ ไม่ใช่แค่ “ยังไม่ได้ทำ”

สมมุติเราสร้างไฟล์:

```text
carts/api/mutations.ts
```

ทั้งที่ไม่มี UI/use case ใช้ ผลคือ:

- code surface เพิ่ม
- tests เพิ่ม
- cache invalidation complexity เพิ่ม
- คนอ่านเข้าใจผิดว่า feature support cart editing

Architecture ที่ดีไม่ใช่ architecture ที่มีไฟล์เยอะ แต่คือ architecture ที่ **สะท้อน capability จริง**

# Phase 14 — Relationship กับ Users

มีสองวิธีดู Cart ของ User:

```text
/carts?userId=5
/users/5/carts
```

แต่ semantics ต่างกัน:

### `/carts?userId=5`

Commerce-centric view

```text
Carts Module
-> filter owner
```

### `/users/5/carts`

User-centric relation view

```text
User Detail
-> inspect that user's carts
```

ทั้งสอง route มีเหตุผลอยู่ร่วมกันได้แม้ข้อมูลมาจาก domain relationship เดียวกัน

Reference User relation:

# Common Mistakes

## 1. สร้าง CRUD ทั้งชุดเพราะ copy Users

แก้: scope ตาม requirement

## 2. Owner filter อยู่ local state อย่างเดียว

แก้: `userId` อยู่ URL search params

## 3. Cart list fetch Users เอง

แก้: reuse Users Directory query

## 4. Detail link ใช้ `<a href>`

แก้: AppLink/TanStack Router

## 5. ทุก transition แสดง full Skeleton

แก้: `keepPreviousData` + fetching bar

## 6. Query key ไม่รวม `userId`

ผล: owner filters คนละผลลัพธ์ชน cache กัน  
แก้: list key ใช้ input object
